# Nexa 真实业务使用问题审查报告

> 审查对象：`stephenbanana77/Nexa`
>
> 首次审查版本：`5905f612`（2026-08-12）
>
> 首次审查时间：2026-08-27；复测时间：2026-08-28
>
> 视角：把 Nexa 当作一个团队准备使用的 AI 数据分析工具，而不是只看 Demo 是否能展示。

## 一、结论摘要

Nexa 已经具备一个有吸引力的技术原型形态：用户可以注册、创建项目、上传 CSV/Excel、配置语义层、生成 SQL-backed 报告，并查看运行轨迹和证据链。SQL AST 安全策略、运行 lineage、自动调查、假设引擎和决策摘要，是项目区别于普通“LLM + CSV”Demo 的地方。

但以真实业务标准衡量，目前不建议直接用于生产决策或连接生产数据库。最主要的风险不是系统报错，而是生成“形式完整、证据充分、业务含义错误”的结论。当前自动语义层会把 `Row ID`、`Postal Code` 等技术字段当成业务指标，导致报告看起来可信，却回答了错误的问题。

建议当前定位为：

> 单用户或小范围、非敏感数据的分析原型，以及可信 AI 数据分析架构的展示项目。

在修复业务语义、安全边界和首次部署问题之前，不应定位为企业 BI 平台或生产级多租户服务。

## 二、实际验证结果

> 说明：本节 2.2 及之后的部分保留首次审查时的原始证据；已修复项和本次复测结果见 2.4。

### 2.1 Demo 主路径

本地启动后实际完成了以下流程：

1. 注册并登录用户。
2. 创建 Superstore Demo 项目。
3. 自动生成数据集、语义层和 Insight Report。
4. 查看 Data、Semantic Layer、Reports、Chat 页面。
5. 发起自然语言问题 `What is total sales by region?`。

Demo 页面可以正常展示：9,994 行数据、21 个字段、9 个 SQL evidence blocks、5 个 investigation cards、Decision Brief 和 Analysis Graph。

### 2.2 自动生成的错误业务口径

Superstore 数据的自动语义层包含：

- `Total Row ID = SUM("Row ID")`
- `Total Postal Code = SUM("Postal Code")`
- `Total Sales = SUM("Sales")`
- `Total Profit = SUM("Profit")`

报告随后优先使用第一列数字字段和第一列非数字字段，产生了以下结果：

- 总 Row ID：`49,945,015`
- 头部 `Order ID` 对 Row ID 的贡献率：`0.17%`
- “为什么该 Order ID 在 Row ID 上领先？”
- “Row ID 数值离群分析”

这些 SQL 可以执行，报告也有证据链，但 `Row ID` 是行标识符，`Postal Code` 是邮编，不应默认作为可加总经营指标。该问题会把技术字段错误包装成业务洞察，是当前最高优先级风险。

相关实现：

- `backend/services/semantic_layer.py:93-119`：所有数值列自动生成 `SUM` 指标，所有非数值列自动生成维度。
- `backend/services/analysis_reports.py:823-846`：使用第一数值列和第一维度列作为报告主分析对象。

### 2.3 未配置 LLM 时的失败体验

在未配置有效 API Key 的环境中，后端确实收到上游鉴权失败，但前端最终显示：

- `Analysis complete`
- `SQL unknown`
- `2 retries`

用户容易把一次失败误认为分析完成。对于数据决策工具，这种错误成功状态比明确报错更危险。

相关实现：

- `backend/api/chat.py:150-168`：流式异常只发送 `error` 事件并结束。
- `frontend/src/pages/ChatPage.tsx:187-196`：收到错误后仍继续用默认值组装 assistant 消息，默认内容为 `Analysis complete`。

### 2.4 2026-08-28 复测与新增问题

使用真实浏览器流程重新注册用户、创建 Superstore Demo、打开报告并发送“各产品分类的销售额排名前5名”后，发现两个首次审查未覆盖的阻断问题：

1. **数据集重复加载导致聊天接口 500（已修复）**

   Demo 报告生成后，DuckDB 中数据集对象可能是 `VIEW`。聊天请求再次加载同一数据集时只执行 `DROP TABLE`，触发 `CatalogException: Existing object ... is of type View`，接口返回 500。现在按实际对象类型安全删除 table/view，并增加回归测试；同一数据集重复生成报告和发起聊天不再因对象类型失败。

2. **未配置 LLM 时前端错误事件渲染崩溃（已修复）**

   未配置有效 API Key 时，上游返回的验证错误是结构化对象。前端直接把 `data.message` 传给 Ant Design 消息组件，React 报 `Objects are not valid as a React child`，用户只看到空白聊天区。现在对字符串、数组和结构化错误统一转换为可读文本；SSE 仍明确返回 `error`，不会生成“Analysis complete”假成功消息。

3. **自动报告把高基数日期误当作业务分组（已修复）**

   Superstore 的 `Order Date`/`Ship Date` 是文本列，首次报告按字段顺序选择 `Order Date`，导致“Top Order Date by Sales”和按单日的集中度结论，业务上不可解释。现在自动报告排除日期/时间字段，并优先选择 Region、Segment、Category 等低基数业务维度；复测报告生成了 `Top Region by Sales` 等可解释分组。语义层仍保留日期维度供用户明确发起时间分析。

## 三、问题清单

### P0：自动语义层会生成错误业务结论

**影响**

业务用户不一定能发现指标选错，容易把技术字段的聚合结果当成销售、利润或运营结论。SQL 和 lineage 只能证明计算过程，不能证明指标口径正确。

**证据**

`seed_semantic_layer_from_schema` 对所有数值列直接创建 `SUM` 指标，没有识别 ID、编码、邮编、序号或技术字段。`generate_report` 又按字段顺序选择第一指标和第一维度。

**建议**

- 对 `id`、`code`、`key`、`row`、`index`、`zip`、`postal` 等字段默认标记为“不可聚合”，而不是自动创建 `SUM`。
- 自动识别只能作为候选，首次生成报告前要求用户确认主指标、主维度和业务定义。
- 为指标增加 `approved`、`semantic_role` 或类似状态，未确认的指标不得进入高置信度决策摘要。
- 在评估中加入“业务语义正确率”，不能只测 SQL 是否能执行。

### P0：全新数据库的 Alembic 首次迁移失败

**影响**

README 推荐的 Docker 启动命令在空数据库上会卡在迁移阶段，团队无法通过标准方式完成首次部署。

**复现**

```bash
tmpdb=$(mktemp /tmp/nexa-alembic.XXXXXX.db)
DATABASE_URL="sqlite:///$tmpdb" alembic upgrade head
```

实际错误：

```text
sqlite3.OperationalError: no such table: runs
ALTER TABLE runs ADD COLUMN lineage JSON
```

**原因**

- `backend/alembic/versions/001_initial.py:19-20` 的 `upgrade()` 是空实现。
- `backend/alembic/versions/002_run_lineage.py:18-20` 直接给不存在的 `runs` 表增加字段。
- `backend/Dockerfile` 启动时执行 `alembic upgrade head`。

**建议**

把当前模型的完整建表逻辑放进 `001_initial.py`，并在干净的 SQLite 和 PostgreSQL 数据库上执行升级、降级和重复升级测试。开发环境的 `create_all()` 不能替代生产迁移。

### P0：Notebook 存在跨用户越权读写和执行

**影响**

只要登录，用户就可以通过猜测或获得其他用户的 `cell_id`，修改、删除或执行对方 Notebook 单元格。

**复现**

使用账号 A 创建 Notebook 和 Python cell，再使用账号 B 请求：

```text
PUT  /api/notebooks/cells/{cell_id}       -> 200
POST /api/notebooks/cells/{cell_id}/execute -> 200
```

实际复核中两个请求都返回 `200`。

**证据**

- `backend/api/notebooks.py:98-113`：更新 cell 时只按 `cell_id` 查询。
- `backend/api/notebooks.py:133-140`：删除 cell 时没有验证 Notebook 所属项目。
- `backend/api/notebooks.py:143-180`：执行 Python cell 时没有验证所属用户。

**建议**

每个 cell 操作都通过 `Cell -> Notebook -> Project -> User` 链路校验归属，校验失败统一返回 404。Python 执行还需要独立进程/容器、CPU/内存/时间限制和网络隔离，当前的受限 `__builtins__` 不能视为安全沙箱。

### P0：LLM 设置是全局配置，任意用户可修改

**影响**

一个用户修改模型、Base URL 或 API Key，会影响整个服务的所有用户。API Key 还会被写入服务端根目录 `.env`，不适合多租户部署。

**证据**

- `backend/api/settings.py:103-120`：已认证用户可以直接更新全局 `settings` 并写入 `.env`。
- `backend/api/settings.py:97-100`：返回的是全局 provider 状态，而非用户级配置。
- `backend/models/user.py` 虽有 `ApiKey` 模型，但 LLM 调用路径没有使用用户级密钥。

**建议**

将 provider 配置和密钥按用户或组织存储，使用 KMS/密钥管理服务或至少服务端加密；Base URL 必须做 allowlist，避免把服务变成任意出站请求代理。管理员级全局配置和普通用户个人配置应分开。

### P1：Connection 接口缺少项目归属校验

**影响**

连接列表和删除接口接收 `project_id`，但没有确认项目属于当前用户。跨用户请求可以得到 `200`，实际连接资源是否存在取决于资源 URI 查询。

**证据**

- `backend/api/connections.py:85-92`：`list_connections` 没有查询 `Project.user_id`。
- `backend/api/connections.py:95-103`：`delete_connection` 没有验证项目归属，也没有检查删除结果。

**建议**

复用项目归属校验 helper；删除时同时校验 URI 中的资源是否属于指定项目和当前用户，并对不存在资源返回 404。

### P1：就绪探针在 SQLAlchemy 2 下恒定失败

**影响**

容器编排平台会把服务判定为未就绪，即使应用本身已能处理请求。

**复现**

```bash
curl -i http://localhost:8000/api/health/ready
```

当前返回 `503`，错误为：

```text
Textual SQL expression 'SELECT 1' should be explicitly declared as text('SELECT 1')
```

**证据**

`backend/main.py:63-73` 使用 `db.execute("SELECT 1")`，SQLAlchemy 2 要求使用 `text("SELECT 1")`，同时应确保异常路径关闭 session。

### P1：流式分析失败后被前端渲染成成功

**影响**

模型不可用、网络失败或 Agent 异常时，用户看不到清晰的失败状态，可能继续分享空结果或错误结果。

**建议**

- 后端发送 error 后不要生成 assistant 成功消息。
- 前端只有收到带有有效 `insight`/`done` 状态和结果字段时才渲染成功卡片。
- 失败结果应显示失败原因、重试入口和配置入口，不能使用 `Analysis complete` 默认文案。

### P1：运行时连接状态与多 worker 部署不匹配

**影响**

MySQL、PostgreSQL 和 Google Sheets 连接主要保存在进程内的 `engine_registry`。Docker 使用 4 个 Gunicorn worker 后，同一项目请求可能落到不同进程，导致连接状态不一致；重启后连接也不会恢复。

**证据**

- `backend/tools/query_engine.py`：`EngineRegistry` 是进程内单例。
- `backend/Dockerfile`：Gunicorn 启动参数为 `-w 4`。

**建议**

连接定义和凭据应持久化，查询引擎按请求或共享连接池创建；或在明确支持单 worker 前，不要以多 worker 配置发布。

### P2：评估指标还不能代表真实 Agent 质量

**现状**

README 声称离线评估为 12 个案例、SQL policy/execution/semantic accuracy 均为 1.0。但当前 golden SQL 评估主要验证预先给定 SQL 的执行结果，不等于真实 Agent 能从自然语言生成正确 SQL。

**建议**

扩展到 30–50 个真实业务案例，并记录：

- Agent SQL 生成成功率
- SQL 执行成功率
- 结果和业务口径准确率
- 重试修复率
- p50/p95 延迟
- 实际 provider token 与成本

### P2：仓库发布和维护信号不足

当前仓库没有可见的 Release、Star、Fork、Issue 讨论或实际 `LICENSE` 文件；README 虽声明 MIT，但法律授权边界没有通过仓库文件落地。提交主要来自单一维护者，最近提交集中在短时间内，尚未形成长期维护和升级信号。

这不影响个人 Demo，但企业采用时需要补充：

- `LICENSE`
- 版本发布和变更日志
- 安全漏洞报告流程
- 依赖升级策略
- 备份、恢复和数据删除说明

## 四、优点与可保留方向

问题较多，但以下设计值得保留：

- `sqlglot` AST 级只读 SQL 策略，比简单字符串黑名单可靠。
- Run lineage 能记录问题、schema、SQL 尝试、策略判断、结果样本和错误。
- Semantic Layer、Insight Report、Hypothesis Engine 和 Decision Brief 已经形成可复用分析资产的产品雏形。
- 前端有明确的分析阶段反馈、证据块和导出入口。
- 后端测试、前端 lint/build、GitHub Actions CI 和 Alembic 目录说明了作者对工程化的重视。

## 五、建议的修复顺序

### 第一阶段：先避免错误决策

1. 修复指标/维度自动选择，技术字段默认不参与业务聚合。
2. 要求用户确认业务指标和维度。
3. 增加真实 Agent 业务语义评估。
4. 修复失败状态渲染，禁止把异常显示为成功。

### 第二阶段：补安全边界

1. 修复 Notebook、Connection 等全部资源的归属校验。
2. 将 LLM Key 和数据连接改成用户/组织级安全存储。
3. Python 执行迁移到真正的沙箱。
4. 对外部 URL、数据库主机和模型 Base URL 做 allowlist 和审计。

### 第三阶段：修复可部署性

1. 重写完整的初始 Alembic migration。
2. 修复 readiness probe。
3. 明确多 worker 下的连接和任务模型。
4. 增加从空数据库启动、升级、回滚和恢复的 CI 测试。

## 六、最终判断

Nexa 的架构方向是对的：AI 分析不应只返回一句话，而应保留 SQL、证据和可复盘轨迹。当前最需要补的不是更多报告模块，而是“业务口径正确性”和“多用户安全边界”。

在完成 P0 问题修复前，建议只用于个人本地环境、匿名/脱敏数据和技术演示；完成后再考虑小范围内部试点。不要让“有 SQL 证据”替代“指标定义经过业务确认”。
